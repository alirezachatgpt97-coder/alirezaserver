# HTTPS، گواهی IP و Cloudflare در rc.8

## رفتار نصب

نصب پایه ابتدا با TLS موقت self-signed بالا می‌آید. صدور گواهی معتبر تا نصب ادغام و اصلاح دسترسی Xray به تعویق می‌افتد؛ مرحلهٔ اولیهٔ نوا دیگر زودتر از آماده‌شدن ادغام، برای دامنه درخواست مستقل نمی‌فرستد. دامنهٔ انتخاب‌شده برای مرحلهٔ پایانی نگه داشته می‌شود.

در پایان، نصاب درخواست گواهی IP یا دامنه را از مسیر اصلی job نوا انجام می‌دهد؛ snapshot و rollback همان مسیر حفظ می‌شود. صرف بازبودن 443 موفقیت نیست: نام، اعتبار زمانی، تطابق کلید و بررسی عمومی HTTPS با CA معتبر کنترل می‌شوند. اگر درخواست شکست بخورد، داده‌ها و HTTPS موقت/قبلی حفظ می‌شوند، ولی نصب با وضعیت گواهی ناموفق کامل اعلام نمی‌شود. هیچ سؤال دوم برای انتخاب روش TLS در نصب مطرح نمی‌شود؛ شکست با علت روشن و گزارش خصوصی ثبت می‌شود. منوی دستی `alireza tls` فقط ابزار اختیاری مدیر است.

## بدون دامنه: IP

- یک IP عمومی قابل مسیریابی لازم است. IP خصوصی، loopback، link-local، multicast و آدرس مستندات پذیرفته نمی‌شوند.
- Let's Encrypt گواهی IP کوتاه‌مدت می‌دهد؛ اعتبار تقریباً شش روز است. این گواهی در صورت صدور موفق، self-signed نیست و مرورگر نیاز به پذیرش هشدار ندارد.
- HTTP-01 به دسترسی عمومی **TCP 80 روی همان IP** و اتصال خروجی HTTPS برای ACME نیاز دارد. اگر ارائه‌دهنده پورت را بسته باشد، CA در دسترس نباشد یا IP قابل دسترسی نباشد، صدور معتبر تضمین‌شدنی نیست.
- Certbot **5.8.0** داخل `/opt/alirezaserver-acme` جدا از Python سیستم نصب می‌شود؛ `--only-binary=:all:` جلوی ساخت وابستگی‌ها روی VPS کم‌رم را می‌گیرد. نسخهٔ root package ثابت است، وابستگی‌های transitively-resolved در `installed-packages.json` و URL/hashهای دریافت‌شده در `installation-report.json` ثبت می‌شوند؛ کل dependency graph به یک lockfile سراسری ثابت تبدیل نشده است.
- فقط همین IP در config اختصاصی `/var/lib/alirezaserver/ip-acme/` مدیریت می‌شود؛ renewal سایت‌های دیگر `/etc/letsencrypt` دستکاری نمی‌شود.
- timer اختصاصی هر شش ساعت با کمی تأخیر تصادفی موعد تمدید را بررسی می‌کند؛ فرایند دائمی جدیدی ندارد. هنگام عدم نیاز، Certbot گواهی تازه درخواست نمی‌کند.
- هنگام تمدید، نام/SAN، زمان، کلید، config Xray، وضعیت سرویس و HTTPS با زنجیرهٔ معتبر و fingerprint موردانتظار بررسی می‌شوند. شکست راه‌اندازی/سلامت باعث برگشت جفت قبلی می‌شود. اگر مدیر بعداً گواهی اصلی را تغییر داده باشد، تمدید IP آن را بازنویسی نمی‌کند.

## دامنه، بدون Cloudflare proxy

رکورد A باید به IPv4 درست و AAAA ــ اگر وجود دارد ــ به IPv6 درست همین سرور اشاره کند. AAAA اشتباه می‌تواند باعث رسیدن اعتبارسنجی/مرورگر به سرور دیگری شود. CAA باید صدور توسط Let's Encrypt را مجاز کند. HTTP-01 از مسیر `/.well-known/acme-challenge/` روی پورت 80 انجام می‌شود.

آداپتور گواهی حالت standalone را به **webroot** تبدیل می‌کند؛ HTTP listener و Xray برای اعتبارسنجی متوقف نمی‌شوند. hookهای قدیمی stop/start از فرمان جدید پاک می‌شوند. مسیر challenge مستقل از مسیر مخفی و ورود پنل، فقط یک token معتبر و فایل معمولی کوچک را می‌خواند؛ traversal، symlink و درخواست نوشتنی رد می‌شوند.

تمدید دامنه از سازوکار Certbot/renew hook اصلی نوا استفاده می‌کند. در نصب قدیمی دارای renewal config standalone که هنوز گواهی معتبر دارد، صرف upgrade الزاماً renewal config آن را بازپیکربندی نمی‌کند؛ برای تغییر روش همان دامنه، صدور/پیکربندی مجدد آن را از بخش Domain یا `alireza tls` انجام دهید. از force-renewal مکرر برای تست استفاده نکنید.

## دامنه پشت Cloudflare

از همان سؤال اول نوا دامنه را وارد کنید. اگر توکن Cloudflare قبلاً در نوا ذخیره شده باشد و رکورد دامنه در zone پیدا شود، نصاب DNS-01 را بدون تغییر رکورد A/AAAA یا وضعیت proxy انتخاب می‌کند. بدون توکن، HTTP-01 انجام می‌شود؛ حالت ساده DNS only و TCP 80 عمومی است. دامنه، رکورد AAAA و CAA باید درست باشند. برای تغییر دامنه هنگام ارتقای نصب سالم، بدون اجرای دوبارهٔ نصب پایه:

```bash
sudo env NOVA_DOMAIN=panel.example.com bash ./install.sh --repair
```

منوی `sudo alireza tls` همچنان برای مدیریت دستی وجود دارد؛ نصب خودکار آن را باز نمی‌کند. در این منو، انتخاب صریح Cloudflare می‌تواند مطابق workflow اصلی نوا رکورد DNS را تغییر دهد. توکن Zone DNS Edit و Zone Read را فقط در پنل یا ورودی مخفی وارد کنید، نه چت یا argv.

در Cloudflare حالت SSL/TLS را روی **Full (strict)** قرار دهید. **Flexible** با هدایت HTTP به HTTPS می‌تواند redirect loop بسازد. DNS-01 برای اثبات مالکیت به رسیدن درخواست CA به پورت 80 نیاز ندارد، ولی Cloudflare برای نمایش پنل همچنان باید بتواند به پورت HTTPS مبدأ متصل شود. گواهی Origin CA مخصوص اتصال Cloudflare به مبدأ است و جای گواهی عمومی مرورگر هنگام اتصال مستقیم به IP را نمی‌گیرد.

برای دامنهٔ orange-cloud بدون توکن، HTTP-01 تنها وقتی کار می‌کند که تنظیمات proxy/redirect/WAF اجازهٔ رسیدن challenge را بدهند. نرم‌افزار نمی‌تواند بدون مجوز DNS یا دسترسی لازم این محدودیت را دور بزند؛ نصاب در شکست، روش درست را پیشنهاد می‌دهد و موفقیت ساختگی ثبت نمی‌کند.

خطاهای عمومی HTTP 5xx مثل 521/525/526 در بررسی عمومی شکست‌اند؛ 403 به‌عنوان احتمال WAF گزارش می‌شود و قواعد امنیتی خودکار غیرفعال نمی‌شوند.

## دستورها

```bash
sudo alireza                 # English interactive dashboard
sudo alireza tls             # IP / domain / Cloudflare wizard
sudo alireza tls-status      # Native job and certificate status
sudo alireza network         # Read-only DNS / TCP / CA-verified HTTPS checks
sudo alireza doctor          # Existing integration checks
```

منوی انگلیسی وضعیت واقعی سرویس‌ها را هنگام بازشدن می‌خواند؛ refresh پس‌زمینه یا loop بی‌پایان اضافی ندارد. IP/دامنه و توکن برای Gemini یا سرویس تحلیلی ارسال نمی‌شوند. درخواست CA و آزمون عمومی HTTPS طبیعتاً به همان مقصدهای انتخاب‌شده ارسال می‌شوند، بدون cookie نشست مدیر.

## نیاز به VPN

این نسخه plain HTTP عمومی پنل روی 80 را به HTTPS هدایت می‌کند؛ loopback API، پورت پروتکل‌ها و event ارتقای WebSocket تغییر نمی‌کنند. TLS صحیح می‌تواند خطای گواهی یا proxy را رفع کند، اما فیلترینگ IP، اختلال مسیر ISP، DNS محلی کاربر یا WAF کشور/ASN از روی کد به‌تنهایی رفع یا تأیید نمی‌شود.

`alireza support` و `alireza network` نتیجه را **از خود VPS** نشان می‌دهد. برای اثبات مشکل بدون VPN، همان URL را از شبکهٔ کاربر با VPN و بدون VPN مقایسه کنید؛ هیچ نتیجهٔ VPS به‌عنوان آزمون شبکهٔ ایران معرفی نشده است. اگر HTTPS معتبر و سرویس سالم است ولی فقط یک ISP وصل نمی‌شود، سیاست آن شبکه/مسیر یا WAF باید جدا بررسی شود. این پروژه برای حل آن‌ها سرویس VPN اجباری نصب یا قواعد firewall را کورکورانه پاک نمی‌کند.

## پشتیبان و بازگشت

قبل از تعویض جفت سالم، نسخهٔ خصوصی آن در `/var/lib/alirezaserver/tls-backups/<hash>/` با directory 0700 و فایل‌های 0600 نگه داشته می‌شود. snapshot موجود تکراری بازنویسی نمی‌شود. backup جدید افزونه، جفت origin و پوشهٔ certهای نوا را هم شامل می‌شود؛ این فایل‌ها را عمومی نکنید.

`--rollback` ادغام را غیرفعال می‌کند و timer اختصاصی IP را متوقف می‌کند؛ گواهی شش‌روزه خودکار به self-signed قدیمی برنمی‌گردد. قبل از انقضا، TLS قبلی را از snapshot متناظر بازیابی یا renewal دیگری پیکربندی کنید. بازگشت کامل همچنان به snapshot/backup متناظر نیاز دارد.
